## 1. Назначение

Этот документ задаёт единый стандарт качества для задач, выполненных с AI-ассистентами (vibe-разработка, agentic coding, AI-assisted development).

Цель: ускорять разработку без потери управляемости, безопасности и ответственности.

## 2. Область применения

Стандарт применяется ко всем задачам, где код/тесты/конфигурация/документация полностью или частично сгенерированы AI.

Если для конкретного проекта есть более строгие требования, приоритет у более строгих требований.

## 3. Обязательные принципы

1. **Человек несёт ответственность.**
   - У каждого AI-изменения есть назначенный владелец (owner).
   - AI не может быть финальным утверждающим лицом.

2. **Итеративная разработка вместо one-shot.**
   - Обязательный цикл: `сгенерировать -> проверить -> исправить -> перепроверить`.

3. **Явные границы задачи.**
   - До начала фиксируются scope, non-goals, acceptance criteria.

4. **Детерминированные гейты обязательны.**
   - Критичные правила должны быть в CI/hooks/policy checks, а не только в тексте инструкций.

5. **Минимально необходимые права.**
   - Агентам, ключам, токенам и сервисам выдаются только необходимые доступы.

## 4. Definition of Done (базовый чеклист)

Задача считается **Done** только если выполнены все пункты:

- [ ] **Scope зафиксирован:** цель, границы, non-goals, критерии приёмки.
- [ ] **Контекст задан:** есть проектные инструкции для агента (как запускать/тестировать/что нельзя трогать).
- [ ] **Изменения трассируемы:** понятен список изменённых файлов и назначение изменений.
- [ ] **Код-ревью человеком проведено:** reviewer подтвердил корректность и поддерживаемость.
- [ ] **Технические проверки зелёные:** релевантные тесты + линт/типизация (если применимо).
- [ ] **Security-проверки зелёные:** secret scan + dependency scan + базовые secure coding проверки.
- [ ] **Риски зафиксированы:** что не проверено, ограничения, план дальнейшей валидации.
- [ ] **Документация обновлена:** инструкции по запуску/валидации/ограничениям актуальны.
- [ ] **Решение о релизе явно принято:** merge/release или осознанный перенос.

Если хотя бы один пункт не выполнен — статус **не Done** (`Blocked` или `Follow-up required`).

## 5. Гейты по стадиям

### 5.1 До генерации

- [ ] Задача достаточно узкая и проверяемая.
- [ ] Определены acceptance criteria и список «что не менять».
- [ ] Проверено, что в промпт не попадают секреты/PII без разрешённой политики.

### 5.2 После генерации

- [ ] Человек прочитал diff и понял логику изменений.
- [ ] Проверены edge-cases, ошибки и негативные сценарии.
- [ ] Нет небезопасных shortcuts (отключённая валидация, чрезмерные роли, hardcoded secrets).

### 5.3 Перед merge

- [ ] CI прошёл.
- [ ] Security-gates прошли.
- [ ] Есть явное одобрение назначенного reviewer.

### 5.4 Перед прод-выкаткой

- [ ] Есть rollback/feature flag план.
- [ ] Настроены наблюдаемость и алерты по изменённому участку.
- [ ] Назначен ответственный за post-release мониторинг.

## 6. Ролевые ожидания

### 6.1 Junior

- Даёт агенту узкие задачи по тикету.
- Не мержит AI-код без ревью старшего.
- Прикладывает доказательства проверки (логи тестов, выводы, артефакты).

### 6.2 Middle

- Делит задачу на итерации.
- Проверяет архитектурные инварианты и обратную совместимость.
- Отвечает за полноту тестов и корректность миграций.

### 6.3 Senior/Lead

- Определяет guardrails (hooks, deny rules, policy checks).
- Утверждает высокорисковые изменения (auth, payments, secrets, infra).
- Контролирует метрики качества AI-изменений.

### 6.4 Security Champion / AppSec

- Поддерживает обязательные security-гейты.
- Проводит выборочный security review AI-изменений.
- Ведёт каталог типовых уязвимостей и контрмер.

## 7. Красные флаги

- Деплой AI-кода без human review.
- Широкие/админские доступы «чтобы быстрее».
- Отключение CI/security-проверок ради дедлайна.
- Отсутствие владельца изменения.
- Подмена статуса «кажется работает» статусом «проверено и безопасно».
- Авто-одобрение AI собственного результата без независимого reviewer.

## 8. Шаблон отчёта по задаче

```md
- Acceptance criteria:

## Changes

- Затронутые модули:

## Validation

- Ручные проверки:

- Secret scan:
- Dependency scan:
- Доп. проверки:

## Risks
- Остаточные риски:
- План снижения:

## Decision
- Статус: Done / Blocked / Follow-up
- Owner:
- Reviewer:
```

## 9. Минимальные метрики

- Доля AI-assisted задач от общего объёма изменений.
- Дефектность после merge (bug rate) для AI-assisted изменений.
- Доля security-замечаний в AI-assisted PR.
- Mean Time To Detect (MTTD) дефектов в AI-assisted изменениях.
- Процент задач, где DoD-гейты пройдены с первого раза.

## 10. LITE vs STRICT (две таблицы)

### 10.1 “Легкий” DoD для прототипов (LITE)

| Категория | Минимум для Done (LITE) | Когда задача **не Done** |
|---|---|---|
| Scope | Ясно описаны цель, границы и ожидаемый результат демо | Нет формулировки «что считаем рабочим прототипом» |
| Риски и ограничения | Явно зафиксированы допущения и ограничения прототипа | Ограничения не описаны и прототип может быть принят за production |
| Код и архитектура | Реализован основной happy-path без избыточного усложнения | Нельзя воспроизвести сценарий даже на демо-данных |
| Тесты | Есть базовая проверка критичного сценария (ручная или автоматическая) | Вообще нет подтверждения работоспособности |
| Безопасность | Нет явных критических анти-паттернов (hardcoded secrets, публичные ключи, broad admin by default) | Есть известная критическая уязвимость без пометки |
| Данные | Не используются реальные секреты/PII без разрешения и политики | В промпты/репозиторий попали чувствительные данные |
| Review | Есть человеческая проверка diff и результата | Принято “AI сделал — значит ок” |
| Документация | Коротко описано: как запустить, что работает, что не покрыто | Нет инструкции запуска и списка ограничений |
| Решение | Явно указан статус: Prototype Done / Follow-up required | Решение не зафиксировано |

### 10.2 “Жесткий” DoD для продакшна (STRICT)

| Категория | Обязательное условие Done (STRICT) | Блокер релиза |
|---|---|---|
| Scope и контракт | Зафиксированы scope, non-goals, acceptance criteria, совместимость и rollback-стратегия | Нет измеримых критериев приемки или rollback-плана |
| Трассируемость | Назначены Owner и Reviewer, есть история решений и проверок | Нельзя установить ответственного за изменение |
| Качество кода | Соблюдены проектные стандарты, инварианты и архитектурные границы | Нарушены инварианты/контракты |
| Тестовое покрытие | Пройдены релевантные unit/integration/e2e (по матрице проекта), критичные edge-cases покрыты | Критичный путь не проверен, есть падающие обязательные тесты |
| CI/CD гейты | Линт, типизация, сборка, тесты, required checks в CI зелёные | Любой required check красный/пропущен |
| Security baseline | Secret scan, dependency scan, SAST (и/или иные обязательные security checks) зелёные | Критические/высокие findings без утверждённого исключения |
| Доступы и секреты | Принцип минимальных привилегий, секреты не в коде/промптах, доступы ревьюированы | Чрезмерные роли, секреты в репозитории, неконтролируемые токены |
| Эксплуатационная готовность | Настроены мониторинг, алерты, логирование, runbook | Нет наблюдаемости или плана реакции на сбой |
| Данные и комплаенс | Выполнены требования к данным (PII/регуляторика/политики компании) | Нарушены требования хранения/обработки данных |
| Release decision | Формальное go/no-go решение зафиксировано ответственными | Нет явного решения о релизе |

### 10.3 Правило выбора режима

- **LITE**: только внутренние демо, discovery, быстрые гипотезы.
- **STRICT**: всё, что затрагивает пользователей, деньги, персональные данные, доступы, интеграции, инфраструктуру или SLA.
- При сомнении применяется **STRICT**.
