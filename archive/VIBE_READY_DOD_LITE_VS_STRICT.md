# Vibe-ready DoD: LITE vs STRICT

Версия: 1.0  
Дата: 2026-11-03

## Таблица 1. “Легкий” DoD для прототипов (LITE)

| Категория | Минимум для Done (LITE) | Когда задача **не Done** |
|---|---|---|
| Scope | Ясно описаны цель, границы и ожидаемый результат демо | Нет формулировки «что считаем рабочим прототипом» |
| Риски и ограничения | Явно зафиксированы допущения и ограничения прототипа | Ограничения не описаны и прототип может быть принят за production |
| Код и архитектура | Реализован основной happy-path без избыточного усложнения | Нельзя воспроизвести сценарий даже на демо-данных |
| Тесты | Есть базовая проверка критичного сценария (ручная или автоматическая) | Вообще нет подтверждения работоспособности |
| Безопасность | Нет явных критических анти-паттернов (hardcoded secrets, публичные ключи, broad admin by default) | Есть известная критическая уязвимость без пометки |
| Данные | Не используются реальные секреты/PII без разрешения и политики | В промпты/репозиторий попали чувствительные данные |
| Review | Есть человеческая проверка diff и результата | Принято “AI сделал — значит ок” |
| Документация | Коротко описано: как запустить, что работает, что не покрыто | Нет инструкции запуска и списка ограничений |
| Решение | Явно указан статус: Prototype Done / Follow-up required | Решение не зафиксировано |

## Таблица 2. “Жесткий” DoD для продакшна (STRICT)

| Категория | Обязательное условие Done (STRICT) | Блокер релиза |
|---|---|---|
| Scope и контракт | Зафиксированы scope, non-goals, acceptance criteria, совместимость и rollback-стратегия | Нет измеримых критериев приемки или rollback-плана |
| Трассируемость | Назначены Owner и Reviewer, есть история решений и проверок | Нельзя установить ответственного за изменение |
| Качество кода | Соблюдены проектные стандарты, инварианты и архитектурные границы | Внесены изменения, нарушающие инварианты/контракты |
| Тестовое покрытие | Пройдены релевантные unit/integration/e2e (по матрице проекта), критичные edge-cases покрыты | Критичный путь не проверен, есть падающие обязательные тесты |
| CI/CD гейты | Линт, типизация, сборка, тесты, required checks в CI зелёные | Любой required check красный/пропущен |
| Security baseline | Secret scan, dependency scan, SAST (и/или другие обязательные security checks) зелёные | Критические/высокие findings без утверждённого исключения |
| Доступы и секреты | Принцип минимальных привилегий, секреты не в коде/промптах, доступы ревьюированы | Чрезмерные роли, секреты в репозитории, неконтролируемые токены |
| Эксплуатационная готовность | Настроены мониторинг, алерты, логирование, runbook/операционные шаги | Нет наблюдаемости или плана реакции на сбой |
| Данные и комплаенс | Выполнены требования к данным (PII/регуляторика/политики компании) | Нарушены требования хранения/обработки данных |
| Release decision | Формальное решение о релизе зафиксировано ответственными | Нет явного go/no-go решения |

## Примечание по применению

- Используйте **LITE** только для внутренних демо, discovery и быстрых гипотез.
- Любая задача, затрагивающая пользователей, деньги, персональные данные, доступы, интеграции, инфраструктуру или SLA, переводится в **STRICT**.
- Если есть сомнение, применять **STRICT**.
